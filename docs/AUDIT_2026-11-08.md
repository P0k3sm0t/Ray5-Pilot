# Performance and stability audit - November 8, 2026

The initial audit was performed without machine motion. No release, version bump,
launcher rebuild, firmware writes, or laser firing was performed. A separately
authorized motion follow-up is documented below. Existing dashboard layout, element
IDs, routes, and command formats were preserved.

## Scope

Reviewed application lifecycle and request handling; job import, validation, bounds
and framing; HTTP commands and status monitoring; camera snapshots, streaming and
timelapse; config persistence; dashboard polling; updater and launcher paths.
Existing uncommitted work was preserved. This is not a claim that every possible
firmware, camera, network failure, or G-code dialect has been verified.

## Findings fixed

| Area | Problem | Fix |
| --- | --- | --- |
| Job lists | Every refresh read and parsed all imported G-code again. | Bounded 256-entry bounds cache, invalidated by size and nanosecond file timestamps. Cached results are copied before returning. Safety validation is not cached. |
| Watcher | Retained unchanged source files were hashed every poll; signatures lost subsecond changes. | Remember verified source/target metadata, avoid repeated hashing, notice fast same-size edits, and prune removed source state. Oversize files are skipped before hashing. |
| Dead state | Imported hash signatures were accumulated but never read. An obsolete cached-status helper had no callers. | Removed this unused state and helper. |
| G-code safety | A limited-line scan first loaded the entire file. A single or compact extrusion move could evade rejection. | Read only the configured line prefix; reject single and compact extrusion moves, ignoring extrusion text inside comments. |
| Bounds | XY-only modal moves were ignored, inches were not converted, M9 incorrectly cleared laser state, and G90.1 could change distance mode. | Preserve modal movement, convert inch coordinates to mm, keep coolant state separate, and match exact distance-mode codes. |
| Frame and jog input | NaN, infinity, and invalid feed values could reach command formatting. | Reject nonfinite bounds/margins/feed and invalid jog numbers; return a clear failure. |
| Manual jog | The required M5 response was ignored. | Do not send the jog when the configured laser-off precondition fails. |
| Stop and command batches | Stop could interrupt the controller but leave a frame batch sending its remaining lines. | Cancel the unsent remainder of pre-existing batches when an enabled Stop is requested. The configured Stop sequence and real response errors are unchanged. |
| Manual controls | Busy state disabled Stop, and resetting busy state could re-enable a disabled laser-test button. | Keep Stop callable during pending manual actions, track overlapping request completion, and retain the configured laser-test lockout. |
| Config | Concurrent saves shared one temporary filename; merged defaults shared mutable nested objects. | Serialize saves, use unique same-directory temporary files and atomic replacement, and deep-copy merged values. Reject nonfinite settings and handle non-object config files without crashing load. |
| HTTP snapshots | Reading response.content from MJPEG could wait indefinitely and grow memory. | Read chunks until the first complete JPEG, enforce elapsed-time and 20 MB bounds, and close the HTTP response on success/failure. |
| Camera resources | A failed stream-open path did not release VideoCapture. | Release the failed capture before reconnecting. |
| Snapshot retention | keep_last=0 deleted all history; matching filename prefixes could include latest_raw.jpg. | Treat zero as unlimited history and explicitly protect both latest images. Tolerate files disappearing during snapshot listing/cleanup. |
| Dashboard reads | Polls could overlap or wait indefinitely; initial/background failures became unhandled rejections. | Coalesce identical in-flight status/jobs/console reads, disable GET caching, bound read timeouts, and catch background poll failures. Machine actions/uploads are neither coalesced nor automatically retried/aborted. |

## Measured result

A temporary, generated 360,010-byte job with 24,000 motion lines was listed six
times using the previous committed JobManager and the updated implementation.
Median warm refresh time was **343.23 ms before** and **0.83 ms after** (about
413x faster in this local microbenchmark). First-parse costs remain: 345.64 ms
before and 366.59 ms after in this run. The speedup is for unchanged files, not
laser motion, upload bandwidth, or every dashboard request.

## Remaining limitations and deliberate non-changes

- Wi-Fi Stop cannot undo commands already accepted by the controller, and an
  in-flight HTTP request can delay delivery. It is not a physical emergency stop.
- Live MJPEG still opens an RTSP connection per viewer. A shared producer could
  reduce multi-tab camera load, but requires a separate lifecycle/concurrency change
  and camera soak testing. No camera transport or output-resolution changes here.
- The bounds parser is not a complete RS-274 interpreter. Advanced work-coordinate
  transforms, subprograms, macros and some arc modes still need dedicated handling.
  Existing LightBurn bounds comments and approximate-radius-arc warnings remain.
- First-time analysis of a large job still performs bounded synchronous work.
  Moving analysis to background workers is a larger change, not part of this patch.
- At the initial audit checkpoint, launcher dependency installation checks, the large
  app.py structure, full multi-client stress testing, and end-to-end update/rollback
  testing remained future work. Later isolated updater tests are documented in
  UPDATER_TEST_2026-11-08.md. Full multi-client and clean EXE first-run tests remain
  uncompleted; packaging checks do not establish them.
- No live motion, Stop, or laser-fire test was repeated during the initial audit. Their
  changed edge paths were tested offline; firmware settings were not edited.

## Complete GRBL settings-read follow-up

The collector previously accepted any settings plus any ok, even when the ok
preceded the dump or a settings tail was still arriving. It could publish only
seven entries as a successful read.

- Require a trailing acknowledgement after the latest settings, plus a short
  payload-settle interval. Status broadcasts do not extend that interval.
- Require standard Ray5/GRBL core settings and retain the last complete key set
  for the same upstream device. Do not hardcode the machine's 46-entry count.
- Serialize settings/identity reads, retry an incomplete dump once, and return a
  failed read with no partial settings if it remains incomplete. Keep partial raw
  output available for diagnostics, not as a successful replacement.
- Apply the ordered/settled response handling to $I too. Fix the backup fallback's
  obsolete, undefined read helper and reject incomplete backup reads.
- Add 16 offline collection tests covering stray/early acknowledgements, delayed
  chunks, missing keys/terminators, stale data, HTTP-only replies, and retry limits.
  All 72 Python tests and the GRBL browser suite passed.
- After restart, the real GRBL page passed its initial read plus 10 consecutive
  refreshes. Every read returned all 46 unchanged settings, with refreshes taking
  approximately 1.7 seconds. The ESP32 page/read-only status query also passed.
- Firmware settings were not saved. No motion, resets, homing, or laser firing was
  performed in this follow-up. Layout and release version remain unchanged.
